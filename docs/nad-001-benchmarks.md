# NAD-001 scale benchmarks

Measured 2026-07-16 on the Windows development host with CPython's standard
`sqlite3` module. Fixtures were generated by
`tests/python/make_scale_fixture.py` at a 1:1.5 item-to-link ratio. Each tier
ran one warm-up followed by five timed calls; p95 is the nearest-rank value.

The query was the bundled `role-active-work-and-attention` saved query for
`project-manager`. The traversal was FFP-1-shaped: one launch root, incoming
depth-one `part-of-launch` membership, then two context levels across active
`depends-on` and `coordinates-with` edges with 500-node/1,000-edge caps.

| Items | Links | Query p95 | Traversal p95 | NAD-001 verdict |
|---:|---:|---:|---:|---|
| 1,500 | 2,250 | 59.85 ms | 102.48 ms | Green |
| 5,000 | 7,500 | 192.23 ms | 293.15 ms | Green |
| 20,000 | 30,000 | 735.45 ms | 1,237.88 ms | Rethink threshold |

The 5,000-item gate passes: query is below 250 ms and traversal is below
500 ms. The implementation uses the first prescribed scale optimization—a
per-call in-memory relationship adjacency index—and keeps SQLite authoritative
and read-only.

The 20,000-item tier intentionally records the rethink boundary. Traversal
exceeds one second there, and merely reaching 20,000 items independently
triggers the NAD rule. If the live workspace approaches that size, evaluate a
rebuildable extension-local cache (PGlite, DuckDB, or SQLite-attached) carrying
the same schema/registry/source watermark. The cache must remain disposable
and must never become tracker authority. A host feature request is the final
escalation, not the first.
